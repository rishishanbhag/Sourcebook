# India GCC Registry

A private, sourced record of India's Global Capability Centres (GCCs). Every fact is stored with the source it came from, the date, how it was collected and a confidence level. Where sources disagree, the app shows every value and marks the field "disputed"; it never picks a winner silently.

- Stack: Vite, React, Tailwind (frontend); Node scripts run with `tsx`; Supabase (Postgres plus one Edge Function); Cloudflare Turnstile; hosted on Vercel.

## 1. Status: a sourced record, not yet a source of truth

"Single source of truth" is the goal. Today this is a **single place where every fact sits next to its evidence**, not a verified or complete list.

- It lists **1,249 sites** (Hyderabad 296, Mumbai 280, Bengaluru 262, Chennai 242, Pune 169; one Bengaluru site is from a press release), mostly from two commercial web directories. That is **33.50%** of the 3,728 sites Nasscom-Zinnov counts (the Overview shows this).
- The directory lists have not been checked against a primary source, and their terms of use have not been checked.
- **No legal entities are linked yet.** 48 GLEIF matches were proposed by Claude and are not reviewed by a person, so the build skips them (section 6).
- Of the sources copied from the project brief, only Nasscom-Zinnov has been fully checked. Six sources have no URL: CBRE, CII-Deloitte, Savills, Vestian, the Economic Survey (its figure was seen in news coverage, not in the PDF) and the MCA master. All except the Economic Survey are marked `[UNVERIFIED]`; so are the Karnataka and Maharashtra policy copies, which are third-party hosted.
- Still thin or empty: talent cost, rents for Chennai, Hyderabad and Mumbai, opening years, and most providers.

## 2. How it fits together

```
 Sources                    Ingest scripts                  Store                    Build               Serve
 data/raw/*.txt (directories) ► load-directories.ts ─┐
 GLEIF API / MCA dumps       ► gleif.ts, import-mca ─┼► match.ts ─► review ─┐
 hand-edited facts           ► edit data/*.csv ──────┤                      ▼
 public Submit form          ► Edge Function submit ─┘   Supabase Postgres ◄─► data/*.csv (export + offline fallback)
                                                                    │
                                                             scripts/build.ts  (validate, resolve claims, score)
                                                                    ▼
                                                             public/db.json ─► Vite + React app on Vercel
```

- **Postgres is the source of truth** when `SUPABASE_URL` and `SUPABASE_SERVICE_KEY` are set in `.env`. Without them everything runs from `data/*.csv`.
- **`data/*.csv` is an export and the offline fallback.** Scripts that write through `scripts/db.ts` (`load-directories`, `match`) update Postgres and refresh the CSV together. `npm run export:csv` pulls every table from Postgres into `data/*.csv`.
- **Reads are static.** `build.ts` writes one `public/db.json`; the browser fetches it once. There is no API at read time.
- **The only browser write path** is the Submit form, which calls the `submit` Edge Function (section 9).
- **If Postgres is unreachable at build time**, each read is retried, then `build.ts` builds everything from the committed `data/*.csv` and prints a warning. Run `npm run export:csv` after changing data in Postgres so that snapshot is fresh.

## 3. The data

### Tables

| Table (`data/*.csv`, Postgres) | Holds |
|---|---|
| `sources` | Every place a fact can come from: name, publisher, URL, date, type (govt / industry_body / consultant / broker / press / company / gcc / submission), the source's commercial interest, a terms note |
| `claims` | **Every fact.** One row is one statement from one source: subject, field, value, unit, period, source, dates, method (manual / import / submission / derived), quote, page |
| `parents` | Company groups (e.g. Microsoft). Identity only |
| `entities` | Legal entities in India (name, CIN, state). Identity only |
| `sites` | A GCC location: parent, city, function. Identity only |
| `cities`, `policies` | Cities; state policy documents |
| `providers`, `engagements` | Service providers (legal, recruit, real_estate, eor, advisory) and which GCC they served |
| `match_decisions` | Recorded decisions on whether two records are the same company |
| `submissions` | Postgres only. Public submissions, status pending / approved / rejected. Never copied into `db.json` |

Not in Postgres: `review_queue.csv` and `gleif_candidates.csv` (scratch files regenerated by scripts) and `mca_filtered.csv`.

All columns are text and blank means empty. `build.ts` (`SPEC`) and `supabase/schema.sql` mirror each other, so change both together.

**Key rule:** identity tables hold no facts. A site's HQ country, sector, rent and so on all live in `claims`, so nothing can appear without a source.

### Rules for adding data

- Every fact is a row in `claims` with a `source_id` from `sources`.
- `subject_type` + `subject_id` say what a claim is about (`site` + `s_acme_blr`, `city` + `blr`, `policy` + `pol_ka`, `ecosystem` + `india`).
- Fields ending in `_count` need a `unit` (company / entity / site / unstated) and a `period`. This stops "2,117 companies" and "3,728 sites" being mistaken for the same thing.
- Every site and every engagement needs at least one claim.
- A `gcc_confirmed` engagement needs a claim from a source of type `gcc` or `submission`, not from the provider alone.
- Anonymised case studies: `anonymised=y` and leave `parent_id` and `site_id` empty. The app never guesses the client.
- Never edit an old claim to correct it. Add a new claim; any disagreement then shows up.
- No director names, personal emails, phone numbers or LinkedIn data.

## 4. How a value is decided

Claims are grouped by **(subject, field, unit, period)** and compared after trivial cleanup (commas, "~", "about").

- **All agree:** one value. **They differ:** status `disputed`, every value shown with its source. Nothing is deleted or overridden.
- A "preferred" claim (highest source tier, then newest) is used only for sorting and display.
- Quirk: values are compared as text, so "35-40%" and "35–40%" count as a dispute.

**Confidence score.** Start from the preferred claim's source tier:

| Source type | Weight |
|---|---|
| govt | 0.9 |
| industry_body | 0.7 |
| consultant, broker, gcc | 0.6 |
| press, company | 0.5 |
| submission | 0.4 |

Then **+0.1** per extra independent agreeing source (max +0.2), **−0.2** if the newest claim is over 24 months old, **−0.2** if disputed. **High ≥ 0.75, Medium ≥ 0.5, otherwise Low.** A site's confidence is its best fact, capped at Medium until a legal entity is linked. "Independent" is counted by `source_id`, not by publisher.

The same code (`src/logic.ts`) runs in the build and in the app, so the Method tab cannot drift from it.

**Providers** are ranked by `3 × gcc_confirmed + 1 × self_reported`, ties by name, with the counts shown separately. Providers with no engagements are not listed,.

## 5. The build (`scripts/build.ts`)

Runs before `dev` and on every Vercel build. It collects **every** error, and if there is any it prints them and exits 1 without writing `db.json`, so bad data fails the deploy instead of reaching visitors.

1. Read all tables (Postgres with retries, else CSV).
2. Validate headers, required fields, enums, duplicate ids and date formats.
3. Apply match decisions (section 6).
4. Check foreign keys; auto-link a site to its parent's single entity in the site's state.
5. Claim checks: source and subject exist; `*_count` fields have a unit and period; every site and engagement has a claim; `gcc_confirmed` engagements have a `gcc` or `submission` claim; anonymised engagements name no client.
6. Group claims, resolve them into facts, score confidence, compute coverage against the latest site-unit `gcc_count`.
7. Write `public/db.json`.

## 6. Matching companies to legal entities

The problem: "Acme Technology India Pvt Ltd" in a government register versus "Acme" in a press list. Scripts suggest; a person decides.

1. Get candidates: `npm run gleif` (free GLEIF API; keeps active entities with an MCA registration number whose name starts with the parent's first word) writes `data/gleif_candidates.csv`. Alternatively download an MCA company master into `data/raw/` and run `npm run import:mca -- data/raw/<file>.csv` (keeps active foreign subsidiaries in KA, MH, TG, AP, TN, GJ with business or IT activity codes; drops emails, addresses and directors).
2. `npm run match` scores each candidate against `parents` and writes `data/review_queue.csv`. Score: same CIN = 1.0; same domain +0.5; core-name overlap up to +0.4; same state +0.1; same city +0.1; parent name inside the legal name +0.2. From 0.5 a pair is queued; 0.9 or more is suggested as "same".
3. Fill `decision` (same / different / unsure) and a `note` in the queue.
4. `npm run match` again: filled rows move into `match_decisions` and are never asked again.
5. `npm run build:data`: each confirmed `same` creates the legal entity with sourced claims and links it to the parent's sites in that state.

**Human review is required.** A "same" decision is skipped by the build if `decided_by` is `claude` or its note says "Not yet reviewed". All 48 current rows are in that state, and the build warns about them. To confirm one, set `decided_by` to a person and remove "Not yet reviewed" from the note. 67 more pairs are open in the review queue.

The directory loader uses a cruder rule: companies in the web lists are the same if they share a first word, with a leading "The" ignored and two-word names for Fidelity, Siemens, "American", "First", GE, T-, Western, NCR and Hitachi. That can still merge related group companies (for example Samsung Electronics and Samsung SDS) and split one company written two ways (Nielsen and NielsenIQ), so spot-check it.

## 7. The app (`src/`)

One page, eight tabs, plain black and white. The tab is a `useState` value (no router). Shared pieces are in `src/components/ui.tsx`. Data is `public/db.json`, fetched once and provided through `DbCtx`.

**Every value is a `<Fact>`** (`src/Fact.tsx`): the value, badges, and an "as reported by [publisher] · [date]" line. Clicking opens every claim behind it (source link, date, method, page, quote, the source's commercial interest, a "Suggest a correction" link). Badges: **High** (solid), **Medium** (outlined), **Low** (dashed); **disputed**; **unverified** (a source's note says it has not been checked against the original).

| Tab | What it shows |
|---|---|
| Overview | Coverage ("1,249 sites = 33.50% of 3,728 sites") and every ecosystem-level number, one row per field, unit and period, with disagreeing sources visible |
| Registry | Searchable table of all sites with filters (city, function, country, industry, entity linked); a detail card with site, company and legal-entity facts |
| City pack | One city: rent and talent cost, state incentives, comparable sites, providers with delivery evidence |
| Compare | Two cities side by side, one row per measure and period; "Not yet sourced" where a city has no figure (not zero); a city with no city-level figures at all (Mumbai, Hyderabad, Chennai) shows "Planned" |
| Incentives | States side by side, one row per incentive type; "No published figure" means none found, not zero |
| Providers | Ranked providers with Confirmed, Self-reported and Disputed counts, and an evidence table per provider |
| Submit | Public form to report a figure or a provider engagement (section 9) |
| Method | The rulebook in plain language, reading its numbers from `src/logic.ts` |

## 9. Public submissions

The Submit tab never publishes anything by itself.

```
 browser form ──► submit Edge Function ──► submissions table (status: pending)
 (Turnstile token)  (validate, rate-limit)                │
                                                          ▼
                                       you review, then run: npm run approve -- <id>
                                                          │
                       creates source "sub_<id>" (type submission) + claim / engagement
                                                          ▼
                       POST BUILD_HOOK_URL ──► Vercel rebuild ──► build.ts re-validates ──► new db.json
```

**What the function checks** (`supabase/functions/submit/index.ts`): CORS against `ALLOWED_ORIGINS`; POST under 8 KB; the Turnstile token via Cloudflare `siteverify`; a source link (http/https) or a quote; for a report, a known subject type, subject, field and value, with a unit and period on `*_count` fields and a period that looks like a year or date; for an engagement, a provider and an anonymised flag, and an anonymised engagement may not name a client. At most **5 submissions per hour per IP**; the IP is stored only as a salted hash. Contact email is optional and never shown.

**What approving does:** the submitter becomes a source of type `submission` (weight 0.4, so Low confidence unless others agree). A report becomes one claim; an engagement becomes a `self_reported` engagement plus a claim, and is never made `gcc_confirmed` automatically. `build.ts` re-validates everything, so a bad approval fails the build instead of publishing.

**Security:** row-level security is on for every table with no policies, so the browser's anon key cannot read or write any table. Only the service key (scripts and the Edge Function) can.

**Limits:** submissions are reviewed by hand in the Supabase table editor (no admin page), and `approve-submission.ts` trusts the payload, so a bad subject id breaks the next build until fixed.

## 10. Deployment and configuration

Vercel runs `npm run build` and serves `dist/` (inferred from commits and the docs; there is no `vercel.json`). Supabase holds the data and the Edge Function.

| Variable | Set in | Used by |
|---|---|---|
| `SUPABASE_URL`, `SUPABASE_SERVICE_KEY` | Vercel build, local `.env` | `build.ts` and scripts. Never shipped to the browser |
| `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` | Vercel build | The Submit form (inlined by Vite) |
| `VITE_TURNSTILE_SITE_KEY` | Vercel build | The Turnstile widget |
| `TURNSTILE_SECRET`, `IP_SALT`, `ALLOWED_ORIGINS` | Supabase function secrets | The `submit` function |
| `BUILD_HOOK_URL` | Local `.env` | `approve-submission.ts`, to trigger a rebuild |

One-time database setup: run `supabase/schema.sql` in the Supabase SQL editor, then `npm run import:db`.

## 11. Privacy, legal and neutrality

- Company-level, professional information only: companies, legal entities, city-level sites, provider firms.
- Unresolved, so keep the app private: India's DPDP Act for submissions (optional contact email and hashed IP are stored, never shown); whether quoting these directories and paid reports is allowed; defamation risk of "disputed" labels on providers; each source's terms of use.
- Provider ranking cannot be bought: it reads engagements only, and there is no sponsorship data. Weak signals set a visible flag on a claim; they never remove one.

## 12. What would make it a real source of truth

1. Replace the web directories with primary sources: the MCA company master (needs a free data.gov.in API key), SEC EDGAR Exhibit 21, official state policy documents, REIT tenant lists.
2. Verify the 6 remaining brief sources and add URLs, dates and page numbers.
3. Have a person review the 48 proposed entity links and the 67 open pairs in the review queue.
4. Get GCCs and providers to confirm their own records (the `submission` / `gcc_confirmed` path).
5. Keep publishing coverage as a percentage of official counts, and never claim "every GCC".

## 13. Known gaps

- `review_queue` and `gleif_candidates` are CSV-only scratch files, and `import-mca` writes a file rather than Postgres.
- No admin page for submissions; no CI; no tests for the Edge Function or the UI.
- `db.json` has no version in its name, so browsers may show stale data after a rebuild.
- The Registry joins with `.find` on every render and has no pagination (fine at about 430 sites).
- `supabase/.temp/` is committed and could be untracked.
